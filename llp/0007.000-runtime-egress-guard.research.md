## Findings

### Late loading does not preserve startup interposition

The guard uses Mach-O `__DATA,__interpose` entries, including the NOCANCEL
variants, to catch calls inside other images. The loader's deferred path uses
`dlopen(..., RTLD_NOW | RTLD_LOCAL)` on the main queue. These are different
mechanisms [observed: EAS `resources/egress-guard/guard.c`; loader C `load_one`].

Apple's published dyld source builds interposition tables at launch, before
fixups, then patches shared-cache uses. Its table builder scans launch-loaded
images. See pinned [dyldMain.cpp](https://github.com/apple-oss-distributions/dyld/blob/fd8d0c4d52320ebf64db34f3cb280310d905c5ae/dyld/dyldMain.cpp#L770)
and [DyldRuntimeState.cpp](https://github.com/apple-oss-distributions/dyld/blob/fd8d0c4d52320ebf64db34f3cb280310d905c5ae/dyld/DyldRuntimeState.cpp#L1298)
[observed: published source read, 2026-10-26].

Ordinary late `dlopen` is therefore not a basis for claiming equivalent coverage
of already-loaded frameworks. Use a resident image loaded at process startup as
the candidate; do not add debugger injection, rebinding machinery or a private
dyld patching path to work around this [inferred: source comparison].

### All apps is not all processes

Both the loader constructor and `serve_sim_startup` return unless `TMPDIR`
contains `/Containers/Data/Application/`. `allApps` only means all eligible apps;
the public type has no all-process scope. A loader armed after boot cannot reach
already-running processes that never inherited it. Moving the current guard to
an ordinary app capability would lose system/helper coverage
[observed: `Sources/ServeSimCapabilityLoader/serve-sim-capability-loader.c`,
`src/capabilities.ts`].

The guard and its loader must be available before the first Simulator process
starts, at stable paths that survive the warm service and job. A future
all-process startup scope must remain libSystem-only and must not broaden
camera/capture/clipboard scope or defer enforcement to a daemon's main queue
[inferred: loader scope and constructor constraints].

### Configuration publication is not runtime acknowledgement

`eg_init` caches mode and log path once. Loader config reload skips already-loaded
paths, does not reapply their environment, and does not unload them when removed.
Startup records are ignored by deferred reload. Removing a startup record cannot
undo its interposers [observed: guard C; loader C `load_capabilities` and
`serve_sim_startup`].

Existing `committed` callbacks mean host configuration was published. They are
not acknowledgements from every process. Missing or oversized loader config
currently loads nothing; startup images remain inert when unauthorized. Egress
cannot reuse that failure meaning as permission for direct traffic
[observed: `src/capability-resources.ts`, `src/launch-manager.ts`
`publishPreparations`; loader C `read_config`].

### Previously connected sockets remain usable

The guard checks destinations on `connect`/`connectx` and addressed
`sendto`/`sendmsg`. It has no `send`, `write` or `writev` entries, and its send
wrappers pass calls with no destination through. A TCP or connected UDP socket
opened while allowed can continue sending after a mode change. Merely relaunching
the user app leaves helper and background-process sockets untouched
[observed: EAS `resources/egress-guard/guard.c`].

An image-mapping survey or a new-process connect self-check cannot establish that
old sockets stopped sending. EAS's existing coverage reporter is observational,
collects descendants of every `launchd_sim`, and omits the root itself; it cannot
become an exact-device admission gate unchanged
[observed: EAS `src/steps/utils/localEgressGuard.ts` `parseGuardCoverage`,
`reportLocalEgressGuardCoverageAsync`; `localEgress.ts` `collectSimulatorProcessIds`].

### Warm integration has other boot assumptions

Build-tools deliberately routes local egress to cold startup, shuts down the
selected booted device, and verifies the packaged guard after startup. Warm claim
and Hub adoption reject boot overrides. The guard check runs in a fresh process;
it does not probe existing socket behavior
[observed: EAS `startWarmIosSimulatorSession.ts`, `iosSimulatorSession.ts`,
`warmIosSession.ts`, `localEgressGuard.ts`; Hub `src/index.ts`,
`src/session-owner.ts`; EAS `resources/egress-guard/check.c`].

The Simulator-facing proxy uses fixed loopback port 8899, but the authenticated
tunnel is job-specific. Proxy environment is currently supplied at boot and
CFNetwork follows host proxy settings. A resident guard alone does not update
cached proxy configuration or prove warm services route through the later job's
tunnel [observed: EAS `localEgress.ts` `buildLocalEgressSimulatorEnvironment`,
`configureSystemProxyAsync`; source pointers supplied by EAS owner].

The worker package builds guard/check native artifacts; the standalone launcher
does not ship them. Serve-sim already packages its loader and capture startup
image. Image creation needs an explicit stable serve-sim artifact installation
before warm boot; finding a job-time npm package is too late
[observed: EAS `packages/worker/package.sh`, launcher package manifest;
Hub package manifest and `build.ts`].

## Smallest candidate and unresolved policy

Reuse the existing loader/startup image machinery, per-device capability config,
atomic publication, device launch lock, exclusive registration and resource
rollback. Put a libSystem-only guard and its self-check in serve-sim. Keep the
guard resident from Simulator boot and make policy live; removing it from a
launchd string cannot unload it from running processes. Do not introduce another
owner service, authentication scheme or persistent job registry
[inferred: smallest change surface; task scope].

The concrete implementation surface would be:

- `Sources/ServeSimCapabilityLoader/serve-sim-capability-loader.c` and
  `startup-capability.h`: add narrowly scoped all-process startup/policy access;
  preserve existing app-only deferred loading and libSystem dependency checks.
- `src/capabilities.ts`, `src/capability-config.ts`, `src/launch-state.ts` and
  `src/launch-manager.ts`: reuse registration, config and locking, distinguish
  resident image lifetime from enabled policy, and add strict transition errors.
  Ordinary capability removal and best-effort arming are insufficient.
- A guard/check source directory beside the existing native capabilities,
  `build.ts` and the package manifest: package both artifacts with serve-sim.
  `src/additional-dylibs.ts` already composes loader/capture boot images, but its
  current caller-triggered path is not an unconditional resident-image install.
- EAS/image integration remains a separately coordinated follow-up. Do not edit
  `session-owner.ts` or relax adoption preflight before a concrete compatibility
  contract and the enforcement proof exist.

This is a proposed change surface, not an implementation or an accepted API
[inferred: source mapping].

Two warmup policies have different costs; neither is selected here:

- **Allow during warmup.** Preserves current unrestricted warmup. Enabling block
  later needs data-path checks for existing TCP/UDP descriptors across all
  processes, including destination-less sends, write variants, in-flight calls
  and inherited/transferred descriptors. Closing a snapshot of sockets is not
  atomic and can close an unrelated reused descriptor. A mode-only version must
  refuse warm local-egress admission and retain cold fallback
  [inferred: guard coverage and descriptor lifecycle].
- **Block during warmup.** Keeps the first local-egress job blocked from the first
  covered socket operation, without needing its intent at warm startup. Ordinary
  jobs explicitly relax it after claim. This changes warmup connectivity and
  needs human selection and boot-service validation. It only avoids previously
  permitted outgoing connections if no earlier phase relaxed the policy;
  allow-to-block reuse still needs data-path enforcement or cold fallback.
  Accepted/inherited sockets and uncovered paths remain proof obligations
  [inferred: guard lifecycle].

Recommend proving the resident startup image first. For an initial small warm
integration, block during warmup is the cheaper candidate **if Gabe chooses that
policy**, and only with a verified first-job/never-relaxed boundary. Preserve cold
fallback for an uninstrumented or previously unrestricted device. Arbitrary
off-to-on reuse needs a larger send-path change; do not advertise it from the
small candidate [inferred: recommendation, human review pending].

Live policy should have explicit allow/block values and a generation in the
existing device config; deletion/read/parse failure must block in resident mode.
Evaluate bounded policy reads at guarded calls before adding a watcher cache:
main-queue delivery cannot fence a busy/suspended daemon. Acknowledgement must
mean that the requested generation governs subsequent covered calls; already
in-flight operations require a defined drain/barrier or a failed transition.
Do not call file rename, a watcher event, or a fresh-process check that barrier
[inferred: candidate semantics requiring concurrency/performance proof].

Serialize transitions under the existing exact-device lock. Verify resident
artifact/version and device boot identity before reuse. Preserve the current
single-job-per-VM assumption only after the owner confirms it; two prepared
devices/replacement must each be instrumented. On teardown, block before tunnel
removal, retain an uncertain fence, and report original plus cleanup errors.
Existing best-effort capability startup is insufficient for enforcement. These
are integration requirements, not changes to `--adopt` in this draft
[inferred: source contracts and failure boundaries].

## Validation gates

1. Host mechanism probe: same interposer at exec versus late `dlopen`, with calls
   from the executable and an already-loaded helper. Exercise live mode changes
   on previously connected TCP/UDP sockets with local peers only. This proves
   **macOS host mechanism only**.
2. Isolated host tests for any implementation: all-process startup scope without
   broadening existing scopes; config updates after load; missing/invalid config;
   allow/block/allow/block; concurrent calls and publication; fork/signal behavior;
   rollback/cleanup failures retaining both errors; exact-device independence.
3. Only after coordinating a private native window: boot with pinned resident
   artifacts, enumerate mapped images for the exact launchd tree, and test old
   and new apps, helpers and background services. Test BSD/NOCANCEL, CFNetwork,
   Network.framework, IPv4/IPv6, TCP/UDP and previously connected descriptors.
   Measure leakage around acknowledgement and config/host failure, plus warmup
   service health and runtime overhead.
4. Separately validate proxy routing, capture startup/upstream failure, one-shot
   adoption, recording finalization, replacement devices and cleanup. Later EAS
   hosted acceptance is a separate gate, outside this exploration.

The host worker, serve-sim and chisel remain outside the Simulator guard. Android
has a separate fence. No result here establishes a VM firewall, hostile-code
containment, complete egress enforcement or hosted acceptance
[confirmed: exploration scope; observed: guard injection boundary].

## Confidence and next handoff

The bounded host probe passed on macOS 26.6.2 arm64 with Apple clang 21.0.0.
Exec-time insertion interposed calls from the executable, a linked helper and a
later-loaded helper. Late `dlopen`, with either LOCAL or GLOBAL visibility,
interposed none of those calls. The probe used a synthetic function returning a
distinct value, without a network connection
[observed: isolated host experiment, Codex, 2026-10-26].

A private copy of the existing guard was adapted only to expose a single-thread
mode setter and classify IPv4 loopback peers as remote. Changing the environment
alone still allowed a new connection. Setting the cached mode to block refused
a new TCP connect and addressed UDP send, but already-connected TCP and UDP
delivered through all five tested calls: `send`, `write`, `writev`,
`sendto(..., NULL, 0)` and `sendmsg` without a destination. All peers bound to
127.0.0.1. These adaptations demonstrate the mode-only gap; they are not a guard
implementation or tests of production loopback classification
[observed: isolated host experiment, Codex, 2026-10-26].

Both results are **macOS host mechanism only**, not iOS Simulator coverage.
The design owner acknowledged the bounded host-only scope before it ran. Probe
sources/builds ran in one unique temporary folder, which was removed afterward;
results and reproduction logs remain outside git. No Simulator, VM, DeviceHub,
package/native rebuild or shared dist was used
[observed: experiment execution and cleanup, Codex, 2026-10-26].
